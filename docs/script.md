### A-2. 말하기

- **대본을 그대로 읽지 마세요.** 굵은 글씨(핵심 문장)만 보고 자기 말로 하면 톤이 자연스럽습니다.
- **3초 이상 조용하면 안 됩니다.** CI를 기다릴 때는 대본의 `⏳ 대기 멘트`를 말합니다. 멘트가 끝났는데도 CI가 안 끝나면 화면의 로그를 읽어 주면 됩니다.
- **용어가 처음 나오면 한 번만 풀어 줍니다.** 예: "CVE, 그러니까 공개된 취약점의 고유 번호입니다."
- 말이 꼬이면 멈추고 그 문단 처음부터 다시 말한 뒤 편집에서 잘라냅니다. 편집을 안 할 거면 "정정하겠습니다" 한마디 하고 이어 가면 됩니다.

### A-3. 화면

- 녹화 전에 해상도를 **1920×1080**으로 바꿉니다 (4K 모니터라면 필수).
- VS Code 글꼴과 터미널 글꼴은 **18pt 이상**, 브라우저 확대는 **125~150%**로 맞춥니다.
- **알림을 끕니다** (카카오톡, Windows 알림). 북마크 바와 개인 탭도 정리합니다.
- 창 배치는 VS Code(왼쪽)와 브라우저 GitHub 탭(오른쪽)이고, 슬라이드는 Alt+Tab으로 오갑니다.
- **화면에 나오면 안 되는 것:** 진짜 토큰·비밀번호, GitHub 계정 설정 페이지(이메일 노출), 다른 저장소 목록
- 가짜 키는 화면에 나와도 됩니다. 무작위로 만든 값이라 실제 키가 아닙니다.

### A-4. 녹화 방식

- 교수님 방식대로 **PPT 슬라이드쇼를 켠 채 한 번에 녹화**하고, 시연할 때만 Alt+Tab으로 VS Code나 브라우저로 넘어갑니다.
- 인트로·아웃트로 영상이 재생될 때는 말하지 않습니다.
- 녹화 전에 `docs/recording-guide.md`의 "녹화 전 체크"를 다 끝냅니다. 특히 `tag-demo.yml`을 main에 미리 올려 둬야 합니다. Run workflow 버튼은 기본 브랜치에 있는 워크플로에만 생깁니다.

### A-5. 녹화 후

- [ ] **처음부터 끝까지 한 번 시청합니다** (교수님이 가장 강조한 부분입니다). 소리가 들리는지, 무음 구간이 없는지 확인
- [ ] 파일 속성에서 1920×1080, MP4인지 확인

- [ ] 녹화하고 나면 저장소에 가짜 키 커밋과 `.gitleaksignore`가 남습니다. 시연 기록이므로 정상이고, README "배운 점"에 이 이야기를 쓰면 됩니다.

## C. 대본

> 표기: **[화면]** 무엇을 보여줄지 · **[대사]** 말할 내용 (굵은 글씨 = 꼭 말할 핵심) · **⏳ 대기 멘트** CI 기다리는 동안 · **[명령]** 입력할 것

### [0:00] 인트로 영상

**[화면]** 슬라이드쇼 시작 → 인트로 영상 2개 (Space로 넘김, 영상 중에는 말하지 않기)

### [0:30] 표지 (슬라이드 1)

**[대사]**
안녕하십니까. 아주대학교 사이버보안학과 정준영입니다.
오늘은 **GitHub Actions로 보안 게이트를 만드는 방법**을 소개하겠습니다.
보안 게이트란 코드를 깃허브에 올릴 때마다 위험한 게 섞여 있는지 자동으로 검사하고, 문제가 있으면 빨간불로 막아 주는 장치입니다.
도구는 전부 오픈소스이고 무료입니다. 깃허브 계정만 있으면 오늘 내용을 그대로 따라 하실 수 있습니다.

### [1:00] 오늘 막을 3가지 (슬라이드 2)

**[대사]**
혹시 과제하다가 급해서 API 키를 코드에 그대로 붙여 넣고 깃허브에 올려 본 적 있으신가요?
아니면 인터넷 예제를 복사하면서 몇 년 전 버전의 라이브러리를 그대로 설치한 적은요?
오늘은 이런 실수 세 가지를 자동으로 막아 보겠습니다.
첫째, **비밀키 유출**. 둘째, **취약점이 알려진 라이브러리 사용**.
그리고 셋째는 조금 특이한데요, **보안 도구 자체가 공격당하는 경우**입니다. 실제로 올해 3월에 있었던 사건인데, 마지막에 직접 재현해 보겠습니다.

### [2:00] DevSecOps와 Actions 구조 (슬라이드 3~4)

**[대사]** (슬라이드 3)
DevSecOps는 개발(Dev), 보안(Sec), 운영(Ops)을 합친 말입니다.
핵심은 하나입니다. **보안 검사를 배포 직전이 아니라 코드를 올리는 순간으로 앞당기자.**
문제는 늦게 발견할수록 고치기 비싸지니까요.

**[대사]** (슬라이드 4)
이걸 자동으로 해 주는 게 GitHub Actions입니다.
저장소에 `.github/workflows` 폴더를 만들고 yml 파일을 하나 넣으면, 그게 자동화 시나리오가 됩니다.
`on`에는 언제 실행할지를 적습니다. 오늘은 push할 때마다입니다.
`job`은 깃허브가 빌려주는 가상 컴퓨터, runner 한 대에서 돌아가는 작업이고,
`step`은 그 안에서 실행할 명령 한 줄, 또는 `uses`로 남이 만든 Action을 불러오는 단계입니다.
결과는 저장소 화면에 **초록색 체크나 빨간 엑스로** 표시됩니다.

### [3:30] 시작 상태 보여주기

**[화면]** VS Code: `app/main.py`, `requirements.txt`, `.github/workflows/security.yml`

**[대사]**
오늘 쓸 예제는 FastAPI로 만든 아주 작은 웹 API입니다.
지금 워크플로 파일에는 "Actions가 동작합니다"라고 출력하는 단계 하나만 있습니다. 아직 보안 검사는 없는 상태입니다.
이 저장소에 검사를 하나씩 붙여 보겠습니다.

### [4:00] 시연 1: gitleaks (슬라이드 5 → VS Code)

**[대사]** (슬라이드 5)
첫 번째 도구는 gitleaks입니다. 코드 안의 API 키, 비밀번호, 토큰을 찾아 주는 오픈소스 도구입니다.
두 가지 방법으로 찾습니다. 하나는 **패턴**이고, AWS 키는 AKIA로 시작하는 것처럼 서비스마다 정해진 형식을 알아봅니다.
다른 하나는 **엔트로피**, 즉 무작위성입니다. 사람이 쓴 단어가 아니라 무작위로 보이는 긴 문자열이면 비밀값 후보로 봅니다.

**[화면]** 터미널

**[명령]**
```
python -c "import secrets,string;print(''.join(secrets.choice(string.ascii_letters+string.digits) for _ in range(40)))"
```

**[대사]**
실습을 위해 가짜 키를 하나 만들겠습니다. 무작위 문자 40개입니다. **진짜 키는 절대 이렇게 실습하시면 안 됩니다.**

**[화면]** `app/main.py`의 `WEATHER_API_KEY = os.environ.get(...)` 줄을 `weather_api_key = "<가짜 키>"`로 바꾸기

**[대사]**
급할 때 다들 이렇게 하시죠. 코드에 키를 바로 넣는 겁니다.
올리기 전에 내 컴퓨터에서 먼저 검사해 보겠습니다.

**[명령]** `gitleaks dir . --redact -v`

**[대사]**
바로 잡혔습니다. 파일 이름, 몇 번째 줄인지, 그리고 `generic-api-key`라는 룰에 걸렸다고 나옵니다.
`--redact` 옵션은 결과에서 비밀값을 가려 줍니다. 로그가 남는 곳에서는 꼭 붙이세요.

**[화면]** `stages/01-gitleaks.yml` 열기 → 전체 복사 → `.github/workflows/security.yml`에 붙여 넣기

**[대사]**
이제 이 검사를 깃허브에 붙이겠습니다. 미리 준비한 1단계 파일을 붙여 넣겠습니다. 두 군데만 보시면 됩니다.
첫째, `fetch-depth: 0`입니다. 커밋 기록 전체를 받아 오라는 뜻이고, 이게 있어야 과거 커밋까지 검사합니다. 이 줄이 잠시 뒤에 중요해집니다.
둘째, gitleaks를 공식 Action이 아니라 본체를 직접 내려받고 있습니다. 이유가 두 가지 있습니다.
**gitleaks 본체는 MIT 라이선스인데, gitleaks-action은 버전 2부터 MIT가 아닌 자체 라이선스로 바뀌었습니다.** 오픈소스만 쓰려고 본체를 택했습니다.
그리고 내려받은 파일이 진짜인지 **SHA256 체크섬으로 검증**합니다. 누가 중간에 파일을 바꿔치기하면 여기서 멈춥니다.

**[명령]**
```
git add .
git commit -m "Add gitleaks secret scan"
git push
```

**[화면]** GitHub → Actions 탭 → 실행 중인 워크플로 클릭

⏳ **대기 멘트**
지금 깃허브가 가상 컴퓨터를 하나 빌려서 제 코드를 받고, gitleaks를 설치하고, 검사를 돌리는 중입니다.
이게 push할 때마다 자동으로 일어납니다. 사람이 깜빡할 일이 없는 거죠.

**[화면]** ❌ 확인 → 로그 펼치기 (RuleID, File, Fingerprint)

**[대사]**
빨간불입니다. 로컬에서 본 것과 똑같이 잡혔습니다.
그럼 고쳐 보겠습니다. 키를 지우고 원래대로 환경변수에서 읽게 바꾸겠습니다.

**[화면]** `app/main.py`를 `WEATHER_API_KEY = os.environ.get("WEATHER_API_KEY", "")`로 되돌리기

**[명령]**
```
git commit -am "Remove hardcoded key"
git push
```

⏳ **대기 멘트**
이번에는 키를 지웠으니까 통과하겠죠? 결과를 한번 보겠습니다.

**[화면]** ❌ 다시 실패 (로그의 커밋이 이전 커밋)

**[대사]**
**그런데 또 빨간불입니다.** 왜 그럴까요?

**[화면]** 슬라이드 6

**[대사]**
아까 `fetch-depth: 0`으로 커밋 기록 전체를 검사한다고 했죠.
최신 파일에서는 키가 사라졌지만, 키를 넣었던 커밋은 기록에 그대로 남아 있습니다. 누구나 그 커밋을 열어 볼 수 있습니다.
그래서 실무 원칙은 이렇습니다. **한 번 push된 키는 이미 유출된 것이다. 지우는 게 아니라 폐기해야 한다.**
실제 서비스였다면 발급한 곳에서 키를 폐기하고, 새 키는 코드가 아니라 GitHub Secrets에 넣습니다.

**[화면]** Actions 로그의 `Fingerprint:` 값 복사 → VS Code에서 저장소 루트에 `.gitleaksignore` 새 파일 → 붙여 넣기

**[대사]**
키를 폐기했다면 그 기록은 더 이상 위험하지 않습니다. 그래서 이 탐지 결과를 예외로 등록합니다.
로그에 나온 Fingerprint, 일종의 지문을 `.gitleaksignore` 파일에 넣으면 됩니다.

## E. 개념 보충 (질문 대비)

**Q. 엔트로피가 정확히 뭔가요?**
문자열이 얼마나 예측하기 어려운지를 나타내는 수치입니다. `password` 같은 단어는 낮고, 무작위 40자는 높습니다. gitleaks는 높은 엔트로피 문자열이 `api_key =` 같은 맥락에 나오면 비밀값으로 판단합니다.

**Q. `fetch-depth: 0`이 없으면요?**
checkout은 기본적으로 최신 커밋 하나만 받습니다. 그러면 과거 커밋에 남은 키는 검사하지 못합니다.

**Q. 히스토리에서 키를 아예 지울 수는 없나요?**
`git filter-repo` 같은 도구로 기록을 다시 쓸 수는 있습니다. 하지만 이미 누군가 clone했거나 캐시됐을 수 있으므로, 기록 정리와 상관없이 **키 폐기가 먼저**입니다.

**Q. CVE와 심각도(HIGH, CRITICAL)는 누가 정하나요?**
CVE 번호는 CVE 프로그램이 공개 취약점마다 붙이고, 심각도는 보통 CVSS 점수를 기준으로 분류합니다. Trivy는 여러 취약점 데이터베이스의 값을 모아서 보여줍니다.

**Q. Trivy도 비밀값을 찾던데, gitleaks가 꼭 필요한가요?**
Trivy의 비밀값 검사는 현재 파일 기준입니다. gitleaks는 커밋 기록 전체를 보는 데 특화돼 있습니다. 오늘 시연 1의 "지워도 남는다"는 gitleaks라서 잡힌 것입니다.

**Q. CycloneDX가 뭔가요?**
SBOM을 적는 표준 형식 중 하나입니다(다른 하나는 SPDX). 형식이 표준이라 다른 도구가 읽어서 취약점을 다시 대조할 수 있습니다.

**Q. immutable release는요?**
깃허브 기능으로, 릴리스를 발행한 뒤에는 그 태그와 파일을 바꿀 수 없게 잠급니다. 3월 사건에서 0.35.0 태그가 안전했던 이유입니다. 오늘 쓴 trivy-action v0.36.0도 immutable release입니다.

**Q. 체크섬 검증은 왜 하나요?**
내려받은 파일의 SHA256 값이 미리 적어 둔 값과 같은지 확인합니다. 다운로드 서버나 중간 경로에서 파일이 바뀌면 값이 달라져 워크플로가 멈춥니다. 실제로 3월 사건에서는 악성 Trivy 바이너리(v0.69.4)도 몇 시간 배포됐습니다.

**Q. composite action이 뭔가요?**
여러 step을 묶어서 하나의 Action으로 재사용하는 방식입니다. 시연 3의 tag-demo-action이 step 하나짜리 composite action입니다.

**Q. 공개 저장소에서 Actions는 정말 무료인가요?**
공개 저장소는 깃허브의 표준 runner를 무료로 쓸 수 있습니다. 비공개 저장소는 무료 플랜에 월 사용 시간 한도가 있습니다.
